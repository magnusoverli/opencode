# OpenCode V1 to V2 Migration Strategy

This document defines how users move from the current OpenCode add-on to the
separate **OpenCode V2 Preview**, and how the existing stable add-on eventually
upgrades to V2 without losing its private state.

It complements [`OPENCODE_V2_FUTURE.md`](OPENCODE_V2_FUTURE.md). The Preview is
not ready to import real user data until the security and validation gates below
are implemented.

## Product Identities

| Channel | Name | Slug | Runtime |
|---|---|---|---|
| Stable | OpenCode | `ha_opencode` | Certified V1 until stable V2 promotion |
| Beta | OpenCode Beta | `ha_opencode_beta` | V1 maintenance beta |
| Preview | OpenCode V2 Preview | `ha_opencode_v2_preview` | Pinned V2 beta |

The Preview starts at add-on version `2.6.0b0` and uses independent image,
release tag, changelog, and workflow names. Its unique slug intentionally gives
it a new private `/data` volume. Its manifest uses manual boot and the initial
runtime starts in read-only mode.

## Non-Negotiable Rules

1. V1 and V2 never write the same OpenCode database, auth files, config root,
   state root, cache root, service files, or plugin directory.
2. Migration is copy-on-write. Source V1 data is never moved, rewritten, or
   opened by a V2 writer.
3. Installing Preview does not automatically receive stable credentials,
   sessions, SSH keys, hooks, plugins, or project instructions.
4. The shared `/homeassistant` workspace is not copied or rolled back. Stable
   and Preview see the same live Home Assistant configuration.
5. `SUPERVISOR_TOKEN` is ephemeral authority and is never exported, imported,
   logged, or persisted.
6. Generated config, managed assets, caches, binaries, logs, and temporary files
   are regenerated by the target image rather than copied.
7. There is no reverse V2-to-V1 data conversion. Rollback restores or reuses an
   untouched V1 source.
8. No migration crosses an add-on slug through plaintext shared storage.

## Why Storage Must Be Isolated

V1 and V2 both default to:

```text
~/.config/opencode
~/.local/share/opencode
~/.local/state/opencode
~/.cache/opencode
```

V2 upgrades the shared SQLite database and creates `session_v2` projections,
while V1 continues writing the old session tables. Provider credentials are
imported once from V1 `auth.json` into V2 credential rows. Later V1 and V2
changes do not synchronize. Current V2 also has no importer for V1
`mcp-auth.json`.

Running both versions against one root therefore creates split history and an
unreliable rollback. The add-ons must instead use:

```text
Stable V1 private volume
  /data/.config/opencode
  /data/.local/share/opencode
  /data/.local/state/opencode

Preview private volume
  /data/v2/config
  /data/v2/data
  /data/v2/state
  /data/v2/cache
  /data/v2/home
```

The eventual stable V2 release uses the same `/data/v2/*` layout inside the
existing stable slug and retains the V1 roots as rollback data.

## Two Migration Paths

### Path A: Stable to the separate Preview

Home Assistant gives each slug a private `/data`; Preview cannot and should not
read stable's private volume. Cross-slug migration is therefore an explicit
user-mediated export/import:

```text
Stable V1 exporter
  -> encrypted .ocmig package + one-time recovery code
  -> user transfers ciphertext
  -> Preview importer validates and previews
  -> user confirms
  -> isolated candidate V2 state
  -> V2 conversion and health checks
  -> atomic activation
```

The default Preview experience is **Start fresh**. Every imported sensitive
category is separately selected and initially unchecked.

An exporter must ship in a V1 stable maintenance release before Preview claims
to support migration. The target precursor is a `2.5.x` release after 2.5.3.

### Path B: Stable slug upgraded in place

When stable eventually adopts V2, Supervisor preserves the stable slug's
private `/data` and options. First boot performs a private copy-on-write
migration:

```text
/data/.config/opencode          untouched V1 source
/data/.local/share/opencode     untouched V1 source
/data/.local/state/opencode     untouched V1 source
/data/.ssh                      untouched V1 source

/data/v2/work/<id>              backup-excluded candidate workspace
/data/v2/generations/<id>/      complete candidate generation
/data/v2/current                atomic active-generation pointer
/data/migrations/<id>.json      non-secret journal
```

Every V2 image that can be installed directly over a V1 generation retains the
certified V1 runtime, migration bridge, and a visible legacy-runtime rollback
option. A later image may omit them only when it refuses an unmigrated V1 source
before touching data; users may skip intermediate add-on releases.

## Shared Migration Architecture

Build one versioned migration library with three thin front ends:

1. **V1 exporter** - inventories and securely packages selected source data.
2. **V2 Preview importer** - decrypts, validates, converts, and activates a
   cross-slug package.
3. **Stable in-place orchestrator** - uses the same inventory, conversion, and
   validation code directly against a private source copy.

The shared library owns:

- logical data categories and allowlists;
- envelope schema and compatibility checks;
- archive limits and safe extraction;
- source inventory and ownership classification;
- SQLite backup and V2 conversion orchestration;
- validation reports and migration journals;
- atomic candidate activation;
- idempotency and replay protection;
- secret-safe logging.

It must not own Supervisor options, add-on process supervision, Ingress, or
OpenChamber UI. Those remain channel-specific adapters.

## Filesystem and Process Isolation

The stable in-place layout retains highly sensitive V1 material in the same
private volume. Directory names alone are not a security boundary.

- A root-owned migrator/sidecar may read V1 databases, `auth.json`, SSH state,
  `/data/options.json`, and backup-excluded work directories.
- OpenCode V2 and shell children run as an unprivileged user that can access the
  active V2 generation and approved `/homeassistant` paths, but cannot read V1
  source roots, options, migration work, journals containing private paths, or
  sidecar process credentials.
- Retained V1 roots and migration work use root-only ownership/modes. Active V2
  generation ownership is granted only after validation.
- The V1 fallback starts only after every V2 process and sidecar client stops.
- Real-image tests attempt direct and symlink-mediated reads from OpenCode,
  plugin, shell, MCP, and OpenChamber process identities.

If the Home Assistant base image cannot simultaneously provide approved
workspace writes and these read restrictions, stable in-place migration is
blocked rather than weakening the boundary.

## Data Classification

### Automatically regenerated

Never export or copy:

- generated `opencode.json` or V2 native config;
- image-managed skills, agents, commands, plugin files, and hash manifests;
- generated home briefing, decision digest, focus-mode context, and MCP help;
- `.cache`, temporary directories, logs, downloaded binaries, npm prefix, and
  language-server caches;
- tmux state, active shell processes, OpenChamber browser sessions, service
  registrations, PIDs, sockets, and generated server passwords;
- discovered `SUPERVISOR_TOKEN`, `HA_TOKEN`, ESPHome ingress sessions, and
  Zigbee2MQTT discovery output.

### Shared live state, not migrated

- `/homeassistant` configuration files and Git worktree;
- project `AGENTS.md`, `.opencode`, and project config files;
- add-on development mounts.

The Preview initially disables project OpenCode config, plugin discovery, and
ambient project instruction discovery (`AGENTS.md` and `AGENTS.local.md`). The
first-run report must explain that the workspace is shared live state and that
concurrent stable/Preview edits can conflict.

### Safe preferences

Export as a recommendation report, not as target `options.json`:

- terminal theme, font, cursor, and focus preference;
- MCP enabled/profile preference;
- briefing and decision-note preference;
- sensitive-file restriction preference;
- CPU mode and non-secret feature toggles.

Supervisor owns target options. Preview shows supported recommendations and the
user confirms them in its Configuration page.

### Explicit opt-in categories

| Category | Default | Import rule |
|---|---|---|
| Provider API/OAuth credentials | Off | Encrypted; per-provider selection; validate compatibility |
| Sessions and messages | Off | Encrypted; privacy warning; migrate a cold SQLite backup |
| SSH private keys | Off | High-risk separate confirmation; prefer a new Preview key |
| SSH public config and `known_hosts` | Off | Validate types, permissions, includes, and commands |
| Git identity/config | Off | Reject credential helpers, includes, aliases, and executable signing config unless explicitly supported |
| User-owned global skills/agents/commands | Off | Copy only files proven user-owned or modified; never executable plugins |
| Decision notes | Off | Copy to Preview-owned `/homeassistant/opencode_v2_preview` after previewing count and size |

### Never migrated automatically

- `SUPERVISOR_TOKEN` or discovered Home Assistant session credentials;
- long-lived Home Assistant access tokens and PPQ keys from add-on options;
- arbitrary `env_vars`;
- V1 MCP OAuth state (`mcp-auth.json`); reauthenticate in V2;
- local OpenCode plugins or project plugins;
- root startup hooks and arbitrary files under `/data`;
- shell history, package-manager credentials, and credential helpers;
- private Preview/stable server passwords.

Home Assistant access tokens and PPQ keys are re-entered as independently
revocable Preview options until the privileged sidecar owns those credentials.

## Cross-Slug Transport

### Initial supported transport: encrypted Ingress download/upload

The stable exporter streams an encrypted package as a user-initiated download
through a dedicated Home Assistant Ingress migration endpoint. The user uploads
that ciphertext through the Preview's corresponding endpoint. Responses use
`Cache-Control: no-store`, disable range/caching behavior unless explicitly
tested, and never expose a plaintext package URL.

This avoids mounting `/share` into the stable root OpenCode container. Add-on
maps are static, and a `share` map would expose every shared file to the terminal,
model-driven shell, hooks, and other container processes.

The V1 exporter:

1. Performs an inventory and shows category counts/sizes without values.
2. Requires separate confirmation for credentials, sessions, and SSH material.
3. Creates a cold or SQLite-consistent source snapshot.
4. Generates a random package ID and high-entropy recovery code.
5. Creates a versioned archive from allowlisted entries only.
6. Encrypts it with an audited format such as `age` passphrase encryption.
7. Streams only ciphertext to the authenticated Ingress client.
8. Displays the recovery code once without logging or persisting it.

The Preview importer:

1. Accepts an encrypted `.ocmig` upload through authenticated Ingress.
2. Accepts the recovery code through an interactive secret input, never an
   option, argument, environment variable, URL, or shell history.
3. Decrypts under backup-excluded `/data/v2/work/<id>` with `umask 077`, or
   under an ephemeral tmpfs when available.
4. Validates the full package before changing target state.
5. Shows the import plan and requires final confirmation.
6. Converts and validates a candidate under a new directory.
7. Moves the complete candidate into `/data/v2/generations/<id>`, fsyncs it,
   then atomically replaces the single `/data/v2/current` pointer.
8. Records the consumed package ID and removes uploaded ciphertext, decrypted
   staging, recovery material, and failed plaintext candidates.

The Preview add-on backup policy explicitly excludes `/data/v2/work`. Init
removes abandoned work before OpenCode, OpenChamber, or backup-relevant services
start. An activated generation is normal private add-on state and may be backed
up; incomplete plaintext work is not.

A separately constrained migration helper add-on may support encrypted `/share`
exchange later. Neither OpenCode add-on receives a broad `/share` mount.

Do not use `/share`, `/homeassistant`, `/addon_configs`, `all_app_configs`, or
Home Assistant backups as an implicit cross-slug transport. Backups are for
rollback, not for populating a different slug.

## Migration Package

The encrypted payload contains one versioned envelope plus allowlisted files:

```json
{
  "format": "ha-opencode-migration/v1",
  "id": "<128-bit-random-id>",
  "created_at": "<UTC timestamp>",
  "expires_at": "<UTC timestamp>",
  "source": {
    "slug": "ha_opencode",
    "addon_version": "2.5.x",
    "opencode_generation": "v1",
    "runtime_version": "1.18.25"
  },
  "target": {
    "slug": "ha_opencode_v2_preview",
    "minimum_addon_version": "2.6.0b0",
    "opencode_generation": "v2"
  },
  "categories": ["sessions", "provider_auth"],
  "entries": [
    {
      "logical_type": "session_database",
      "path": "sessions/opencode.db",
      "size": 1234,
      "sha256": "<hex>"
    }
  ]
}
```

The importer rejects:

- unknown envelope versions or target generations;
- expired, previously consumed, or wrong-target packages;
- absolute paths, `..`, symlinks, hardlinks, devices, FIFOs, and sockets;
- duplicate paths or logical identities;
- undeclared or category-incompatible entries;
- hash, size, count, nesting, and decompression-ratio violations;
- unexpected database schema provenance;
- source versions outside the converter's tested compatibility matrix.

No extraction occurs directly over live state.

## Database and Credential Conversion

### Sessions

Never hot-copy a WAL-mode `opencode.db`. The exporter must either stop all V1
writers or use SQLite's backup API to produce a consistent database.

The cross-slug exporter should prefer SQLite's online backup API so exporting
does not interrupt stable use. The stable in-place migration uses a cold path:
stop all known writers, terminate or reject orphan processes, checkpoint WAL,
copy, then run integrity checks. Tests include a source with active concurrent
writers and prove the selected protocol returns one consistent snapshot.

Preview imports the backup into a candidate V1-compatible root, runs the exact
pinned V2 migrator against that copy, and waits for migration completion. It
then verifies:

- source and migrated session counts;
- skipped/invalid message and part counts;
- migration cursor/completion state;
- random sampled session ordering and tool states;
- database integrity and foreign keys;
- absence of writes to the original source.

The report must disclose known lossy conversions. V2-created sessions are not
backported to stable V1.

### Provider credentials

V2 imports V1 `auth.json` only under specific database-upgrade conditions. The
importer must fixture-test the exact pinned V2 build rather than assume that
copying `auth.json` into an empty V2 root triggers import.

Provider credentials use an independent opt-in. If the exact V2 migration
cannot import selected credentials without also importing unrelated state, the
Preview requires reauthentication instead of implementing an unverified custom
database writer.

V1 `mcp-auth.json` is retained only in the encrypted rollback/export package;
it is not activated in Preview.

## State Machine and Idempotency

Each migration has a private non-secret journal:

```text
discovered
inventoried
snapshot_created
package_validated
staged
converted
validated
activated
failed
rolled_back
```

The journal stores IDs, versions, timestamps, category counts, sizes, hashes,
and error codes. It never stores secrets, filenames containing credential
identifiers, recovery codes, prompts, or tool output.

Restart behavior:

- Before activation, discard or resume only a fully validated work generation.
- Config, data, state, and home live under one generation directory. Activation
  fsyncs files and parent directories, then atomically replaces one `current`
  pointer/file on the same filesystem.
- A consumed package cannot be imported again without an explicit reset that
  first removes the target candidate.
- A failed candidate never replaces the last known-good V2 state.

## User Experience

### Preview first run

1. Install **OpenCode V2 Preview**.
2. Choose **Start fresh** or **Import from OpenCode V1**. Import is accepted
   only before the target has V2-created sessions or credentials; there is no
   merge in the initial format.
3. For import, first run the exporter in a supported stable release.
4. Copy the one-time recovery code.
5. Select the encrypted package in Preview and enter the code.
6. Review categories, compatibility warnings, and unsupported settings.
7. Confirm import.
8. Validate provider sign-in, session visibility, MCP health, and workspace
   access before enabling additional options.
9. To return to stable, stop Preview and start stable. Stable private state was
   never changed.

Preview uses manual boot and starts read-only. Editable mode requires stable to
be stopped and requires an exclusive cross-slug workspace lease. A precursor V1
release teaches stable to acquire the same lease before mutating the workspace.
The lease uses an atomic shared lock, heartbeat, Supervisor state checks, and
stale-owner recovery; a warning alone is not sufficient.

### Eventual stable V2 upgrade

1. Mark the V2 stable version as a breaking update.
2. Require a verified cold Home Assistant backup containing the stable add-on.
3. Stop ttyd/tmux sessions, LAN and foreground OpenCode servers, OpenChamber,
   MCP/LSP processes, hooks, and orphan writers; acquire a migration lock and
   prove no database handle remains.
4. Inventory V1 state and check free space.
5. Build and validate an isolated V2 candidate.
6. Atomically select V2 and start health checks.
7. On failure, select the retained V1 runtime and preserve diagnostics.
8. On success, retain V1 source data through the documented rollback window.
9. Offer explicit cleanup only after the user verifies credentials, sessions,
   SSH/Git, MCP, OpenChamber, and workspace editing.

Every V2 image directly installable over V1 keeps old option keys in `schema`
with compatible types so Supervisor does not discard values before migration
code can inspect them. V2-specific options are additive. The V1 fallback uses a
compatibility adapter and never rewrites old values into a shape V1 cannot read.
Tests cover skipped releases, missing/default keys, password options, V2 option
changes followed by fallback, and unsupported direct upgrades.

## Rollback

### Preview

Rollback is operational rather than reverse migration:

- stop Preview;
- start stable;
- optionally uninstall Preview after exporting any V2-only sessions the user
  wants to retain separately;
- never revoke or remove stable credentials automatically.

### Stable in-place

The dependable rollback restores retained V1 OpenCode-private state and the V1
runtime. Replacing only the binary is insufficient. Workspace edits and normal
Home Assistant configuration changes made while V2 ran are live shared state
and are not rolled back by this mechanism; users rely on Git and Home Assistant
backups for those files.

The first stable V2 release keeps:

- untouched V1 config/data/state roots;
- a migration journal and compatibility report;
- the certified V1 binary and launch path;
- a user-visible rollback selector;
- the pre-upgrade Home Assistant backup recommendation.

## Delivery Sequence

### M0: fixture and inventory framework

- Add versioned envelope schemas and logical categories.
- Build synthetic and redacted V1 fixture sets.
- Implement read-only inventory and compatibility reports.
- Prove no secret values enter reports or logs.

### M1: V1 exporter maintenance release

- Add explicit exporter command/page to stable and beta V1.
- Add encrypted Ingress download and recovery-code handling without a `/share`
  mount.
- Initially support preferences and sessions; credential/SSH categories remain
  disabled until dedicated security tests pass.
- Release before claiming Preview migration support.

### M2: Preview importer

- Import only into backup-excluded private `/data/v2/work`, then activate one
  complete generation.
- Run exact-version V2 conversion and validation.
- Add atomic activation, idempotency, replay protection, and cleanup.
- Keep Start fresh as the default.

### M3: sensitive optional categories

- Provider credentials with per-provider confirmation.
- SSH/Git identity with strict validation and permissions.
- User-owned global skills/agents/commands without plugins or hooks.
- Decision notes into Preview-owned shared state.

### M4: stable in-place orchestrator

- Reuse inventory, converters, validators, reports, and journals.
- Add retained V1 runtime fallback.
- Exercise upgrade, failed upgrade, rollback, and retry from real backups.

## Acceptance Gates

### Isolation

- Installing, starting, importing into, or uninstalling Preview changes no file
  in stable private `/data`.
- V1 and V2 never open the same session/auth database for writing.
- Stable and Preview use unique ports, sockets, tmux names, shared state paths,
  service IDs, Ingress paths, and generated config locations.
- Preview defaults read-only; writable stable/Preview sessions cannot coexist
  without an exclusive, tested cross-slug workspace lease.
- Project instructions and root startup hooks remain disabled until the user
  explicitly opts in after acquiring the editable workspace lease.
- The V2 process identity cannot read retained V1 roots, Supervisor options,
  migration work, SSH private keys, or sidecar credentials.

### Export and package security

- No export occurs without user action.
- Sensitive categories require independent confirmation.
- Ciphertext copied by another add-on is unusable without the recovery code.
- Recovery codes and plaintext never enter options, logs, process arguments,
  shell history, telemetry, crash output, or backups. Work/staging paths are
  excluded from Home Assistant backups and wiped on restart before services run.
- Malicious archive fixtures cannot escape staging or exhaust bounded resources.
- Wrong, expired, replayed, truncated, modified, and oversized packages fail
  closed without changing target state.

### Conversion

- Fixtures cover supported V1 add-on and OpenCode versions, WAL databases,
  partial migrations, malformed auth, orphan parts, interrupted tools, and
  missing attachments.
- Snapshot tests include active ttyd/tmux, LAN, OpenChamber, MCP/LSP, hook, and
  orphan-writer scenarios.
- Source database hashes remain unchanged.
- Session and credential differences are reported without content disclosure.
- A crash at every state transition is resumable or safely restartable.
- V1 remains usable after every failed Preview import.
- `auth.json` is in place before the candidate's first V2 database bootstrap;
  credential import and session migration each reach their own completion gate.
- Initial import refuses a target containing V2-created sessions or credentials.

### Stable promotion

- Real Home Assistant backups restore the retained V1 state.
- The V1 fallback starts after a failed V2 conversion or health check.
- V2 OpenChamber, terminal, provider auth, MCP, sessions, SSH/Git, and workspace
  edits pass on both architectures.
- Cleanup is never automatic in the first stable V2 release.
- Every image that accepts a direct V1 upgrade contains the migration bridge and
  V1 fallback; later images fail before mutation when source generation is too
  old.

## Open Decisions

1. Exact audited encryption implementation and recovery-code input channel.
2. Whether the first exporter requires a stopped V1 service or uses an embedded
   SQLite online-backup implementation.
3. First supported source-version matrix and maximum package limits.
4. Whether Preview sensitive imports launch in `2.6.0b0` or a later beta.
5. How V2-only sessions can be exported for archival or future stable import.
6. Retention duration and disk-space policy for stable V1 rollback data.
7. Cross-slug workspace lease format, stale-owner recovery, and stable release
   that first enforces it.

These decisions must be resolved through fixture tests and threat review, not by
copying live user data during initial Preview development.
